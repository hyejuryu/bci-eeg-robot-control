# Session 11

## 1. Objectives

* BrainFlow 기반 EEG acquisition pipeline을 구축한다.
* 실제 Cyton 연결 전에 synthetic board로 save / readback workflow를 먼저 검증한다.
* OpenBCI Cyton을 BrainFlow에서 `CYTON_BOARD`로 연결하고 짧은 recording을 수행한다.
* Session 10에서 확인된 known-good Ch1 forehead flat-electrode montage를 사용해 actual Cyton acquisition pipeline을 검증한다.
* Raw data, metadata, readback summary의 저장 위치를 분리한다.
* 저장된 raw file을 다시 읽어 shape, sample count, duration plausibility를 확인한다.
* Actual raw data와 local metadata가 GitHub에 올라가지 않도록 `.gitignore` 동작을 확인한다.

This session is limited to acquisition infrastructure verification.

## 2. Research question

Session 11의 목표는 EEG feature interpretation이 아니라 BrainFlow 기반 Python 수집 코드 작성과 EEG 데이터 저장 구조 설계이다.

이번 회차의 verification focus는 다음과 같다.

```text
Can the BrainFlow-based Python acquisition pipeline save, document, and read back EEG acquisition data in a reproducible file structure?
```

Session 10에서 posterior dry-comb contact가 unresolved bottleneck으로 남았기 때문에, actual Cyton test에서는 posterior montage를 사용하지 않고 Session 10에서 확인된 known-good Ch1 forehead flat-electrode montage를 사용했다.

이 montage 선택은 unresolved posterior contact issue와 software / file-handling pipeline 검증을 분리하기 위한 것이다.

## 4. Key takeaways

### 1. Synthetic board testing separated software workflow checks from hardware variables

The first part of Session 11 used BrainFlow's synthetic board.

This step did not use real EEG hardware or human biosignal data.

The purpose was to verify the software-level workflow before using actual hardware:

```text
BrainFlow synthetic board
→ short stream
→ raw CSV save
→ readback
→ shape comparison
→ summary JSON
```

This made it possible to check file writing, readback, and summary generation without introducing real Cyton hardware or electrode-contact variables.

Therefore, the synthetic board test functioned as a controlled software pipeline check before actual Cyton acquisition.

### 2. Actual Cyton acquisition was verified with the known-good Ch1 forehead montage

The actual Cyton test used the simplified montage confirmed in Session 10:

```text
Ch1 / N1P
black snap cable
flat electrode A
forehead contact
SRB earclip unchanged
BIAS earclip unchanged
Ch2–Ch8 off or ignored
```

Before recording, the following conditions were checked:

```text
OpenBCI GUI closed
Cyton battery powered
Cyton board switch = PC
USB dongle switch = GPIO6 side
USB dongle connected
COM3 expected
Arduino / robot hardware disconnected
```

COM3 was checked manually. `mode` showed COM3, unplugging the USB dongle removed COM3, and `[System.IO.Ports.SerialPort]::GetPortNames()` also returned COM3.

The actual BrainFlow run completed the following path:

```text
Cyton
→ COM3
→ BrainFlow
→ raw CSV save
→ local metadata JSON save
→ raw CSV readback
→ readback summary JSON
```

The run completed without acquisition failure.

### 3. Actual biosignal recording requires separate handling of raw data, metadata, and verification outputs

Session 11 was the first stage where actual Cyton biosignal recording was saved through the Python pipeline.

For this reason, file separation became part of the acquisition infrastructure.

The output structure was:

```text
data/raw/session-11/
→ actual raw CSV
→ local metadata JSON

results/session-11/
→ readback summary JSON
```

The raw CSV represents the recording itself.

The local metadata JSON records the local acquisition context, including board, serial port, montage, software version, and file paths.

The readback summary JSON records verification results without including raw signal values.

The `.gitignore` policy keeps actual recording files local by default through rules such as:

```text
data/raw/**
data/**/*.csv
```

After the actual Cyton run, `git status --short` showed only the script and readback summary JSON; the actual raw CSV and local metadata JSON did not appear.

This confirmed that the actual recording files were kept local while the verification summary remained repository-visible.

### 4. Readback verification used BrainFlow shape matching and sample-count plausibility

BrainFlow returned the actual Cyton data as a board-specific rows × samples array.

The actual Cyton readback summary reported:

```text
num_rows: 24
eeg_channels: [1, 2, 3, 4, 5, 6, 7, 8]
timestamp_channel: 22
original_shape: [24, 1202]
restored_shape: [24, 1202]
```

This means:

```text
24
= total BrainFlow rows for the Cyton board layout

1202
= samples collected during the short recording
```

The 24 rows reflect the full BrainFlow-defined Cyton board layout, which includes EEG channel rows and other board-specific rows.

The requested duration was 5.0 seconds at 250 Hz.

```text
expected_sample_count = 5.0 × 250 = 1250
actual_sample_count = 1202
difference = 48 samples
estimated_duration_sec = 1202 / 250 = 4.808 sec
```

The current plausibility criterion was:

```text
abs(actual_sample_count - expected_sample_count) < sampling_rate
```

Since the difference was 48 samples and the sampling rate was 250 Hz, the sample count was treated as plausible for this short timing-based stream test.

The readback result was:

```text
shape_match: true
sample_count_plausible: true
```

### 5. The result should be interpreted as acquisition infrastructure verification only

The recording was useful as an acquisition infrastructure check, not as an experimental EEG feature dataset.

## 5. My understanding

Session 11 continued the acquisition-path verification started in Session 10, but moved from GUI-based confirmation to Python / BrainFlow-based acquisition.

The OpenBCI GUI is useful for checking connection, live stream, and visible signal behavior.

BrainFlow is needed for programmatic acquisition and file handling:

```text
connect to board
→ collect data into an array
→ save raw data
→ save metadata
→ read the file back
→ generate verification summary
```

This pipeline is expected to become the basic file-handling structure for later biosignal acquisition work.

The known-good forehead montage was appropriate here because the goal was not posterior alpha testing. It allowed the acquisition and file-handling pipeline to be tested without mixing in the unresolved posterior contact problem.

The current result only verifies the BrainFlow-based acquisition infrastructure. It does not evaluate posterior signal quality or EEG features.

## 6. Questions / unclear points

* How should a soft serial-port preflight check be added before the next actual Cyton recording?

  * It should check available COM ports when possible.
  * It should stop if the requested COM port is clearly missing.
  * It should not become too restrictive across different Windows setups.
  * If COM-port listing is unavailable, the script should record that the pre-check was skipped rather than failing unnecessarily.

* Should the current sample-count plausibility tolerance remain at one sampling-rate interval?

  ```text
  abs(actual_sample_count - expected_sample_count) < sampling_rate
  ```

  This may depend on Cyton streaming behavior, BrainFlow buffering, recording duration, and the impact of missing samples on later analysis.

* When testing posterior acquisition with Ten20 paste and gold cup electrodes, what needs to change compared with the Ch1 forehead infrastructure test?

  Possible differences include electrode type, contact method, montage documentation, contact stability criteria, and whether additional GUI checks are needed before BrainFlow recording.

## 7. Next actions

* Add a soft serial-port preflight check before the next actual Cyton recording.
* Test posterior contact-assisted acquisition using Ten20 paste and OpenBCI gold cup electrodes.
* Document differences between the Ch1 forehead infrastructure test and the posterior contact-assisted setup.
* Update the posterior alpha montage only after the revised contact-assisted setup is actually tested or adopted.
* Proceed to eyes-open / eyes-closed and PSD analysis only after posterior acquisition is stable enough for condition-based recording.
* If posterior acquisition remains unstable, continue acquisition troubleshooting before feature-level analysis.
