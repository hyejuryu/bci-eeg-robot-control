## 1. Objectives

Session 12 was originally planned as a milestone / buffer session for connection errors, noise issues, setup manual updates, and acquisition code refinement.

* Test contact-assisted posterior acquisition using Ten20 conductive paste / gel and OpenBCI gold cup electrodes.
* Check whether the posterior setup can reach stable GUI-level acquisition criteria before BrainFlow recording.
* If posterior acquisition remains unstable, return to forehead baseline recovery and acquisition-path troubleshooting.
* Document setup attempts, screenshots, channel mapping, SRB / BIAS conditions, and recording decisions.
* Decide whether the next project block can proceed with self-recorded eyes-open / eyes-closed data collection, or whether the project should separate OpenBCI acquisition risk from analysis / control development.

## 2. Research question

Can the OpenBCI Cyton setup recover a stable acquisition baseline and support posterior contact-assisted recording, or should self-recorded acquisition be treated as an active project risk?

This session focuses on acquisition stability and troubleshooting evidence.

Feature-level EEG interpretation, alpha reactivity analysis, focus estimation, and robot-control testing are out of scope.

## 4. Key takeaways

### 1. Posterior contact-assisted setup showed temporary improvement but not repeatable stability

The first posterior contact-assisted block tested gold cup + Ten20 acquisition at an approximate posterior position.
S12-A02 showed temporary improvement to a Not Railed Ch1 condition after Ten20 reapplication and improved hair separation.

However, S12-A03 returned to Near Railed under a similar posterior condition.
This suggests that contact-assisted posterior setup can improve contact relative to the initial attempt, but Session 12 did not establish repeatable posterior acquisition stability.

The result does not rule out gold cup + Ten20, but it shows that the current posterior placement / fixation / contact condition was not stable enough for recording.

### 2. The issue was no longer limited to posterior hair contact

After the posterior attempts, a forehead gold cup + Ten20 control was tested, but it remained Near Railed. 
The known-good Ch1 forehead flat-electrode baseline from Session 10 was also attempted again, but it was not reproduced at the end of the initial Session 12 block.

This shifted the troubleshooting focus from posterior hair-contact instability alone to a broader acquisition / contact / reference stability issue.

The remaining possibilities included:

```text
active electrode contact
lead / cable condition
SRB / BIAS contact
GUI / channel state
board / session state
current-session setup instability
```

### 3. Baseline recovery attempts showed partial responsiveness but no stable acquisition baseline

The 2026-07-07 continuation block started from a full reset and attempted to recover a stable forehead acquisition baseline. Ch1 forehead baseline was not recovered. Ch2 showed partial responsiveness under some conditions, especially around the left-forehead flat-electrode setup and SRB assembly B, but the improvement was not stable.

The observed pattern was:

```text
temporary Not Railed or partial responsiveness
→ time-dependent drift
→ Near Railed or Railed state
``

Session 12-C then narrowed the test to one fixed condition: Ch2 / N2P, white snap cable, flat D, left forehead contact position, SRB assembly B, BIAS assembly B, and a fixed observation window. C00 confirmed that the GUI / Cyton / COM3 live-stream path was active after full reset. C01 started in a Near Railed state and eventually drifted to Railed 100% / 0.00 uVrms.

Together, the continuation and controlled check did not recover a stable acquisition baseline. This provided the stopping point for Session 12 hardware testing.

### 4. The project route should separate acquisition risk from analysis / control progress

Session 12 showed that additional self-guided hardware swapping is unlikely to be the most productive use of the next project block unless OpenBCI support suggests a specific test.

The project should therefore separate tracks:

```text
OpenBCI self-recording
= troubleshooting / optional validation track

public EEG
= main analysis backbone

Arduino
= independent control-output track

public EEG replay-control
= bridge between EEG feature variability and actuator command testing
```

The next project block should begin public EEG replay-control and Arduino minimum-demo work while preparing an OpenBCI forum/support inquiry using Session 10–12 evidence.

## 5. My understanding

Session 10 suggested that the main unresolved issue was posterior dry-comb scalp contact through hair.
Session 11 verified the BrainFlow acquisition / save / readback infrastructure using a known-good forehead montage, but did not validate posterior acquisition quality.
Session 12 refined the interpretation.

The posterior contact-assisted setup was not repeatably stable, and the later forehead baseline recovery checks also remained unstable.

The current bottleneck is therefore better described as:

```text
acquisition / contact / reference stability risk
```

rather than only:

```text
posterior hair-contact issue
```

The earlier Session 10 forehead baseline and Session 11 BrainFlow infrastructure check remain valid within their original scope.
Session 12 adds a new constraint: the current self-recorded OpenBCI acquisition condition is not stable enough to support eyes-open / eyes-closed alpha reactivity testing.

The project should not wait for OpenBCI acquisition stability before developing the analysis and control architecture.

A more stable route is:

```text
public EEG dataset
→ sliding-window feature extraction
→ feature time series
→ threshold / smoothing / dwell-time logic
→ command stream
→ Arduino actuator test
```

OpenBCI self-recorded data can be added later if the acquisition issue is resolved.

## 6. Questions / unclear points

* Is the current instability mainly related to SRB / BIAS contact, active electrode contact, lead / cable assembly, GUI / channel state, or board / session state?
* Would OpenBCI impedance checking or another OpenBCI-supported diagnostic help narrow the issue?
* What evidence package should be sent to OpenBCI forum/support?
* How should a public EEG feature replay pipeline be structured so that sliding-window features can drive Arduino commands while keeping replay-based and self-recorded BCI claims separate?
* How can public EEG feature time series be used to analyze variability, threshold sensitivity, latency, and false-trigger-like events?
