# Session 19 — Stored EEG-Derived Command Replay to the Actuator

* **Planned period:** 2026-07-28 to 2026-07-29
* **Actual work dates:** 2026-08-02
* **Documentation finalized:** 2026-08-04
* **Status:** Completed

## 1. Objective

Replay the frozen Session 16 EEG-derived command stream through the
Session 18 Python–Arduino serial interface to the Session 17
servo-gripper actuator, while preserving traceability from each
selected source event to its replay schedule, serial command, Arduino
ACK, and recording-level result.

## 2. Scope

This session included:

* validation of the frozen Session 16 decision-rule record and command
  stream;
* selection of the first command row and subsequent command-state
  changes from each recording;
* mapping from `CMD_STOP`, `CMD_OPEN`, and `CMD_CLOSE` to the serial
  commands `STOP`, `OPEN`, and `CLOSE`;
* recording-specific replay-time construction;
* monotonic-clock command scheduling;
* expected ACK result and actuator-mode validation;
* independent serial execution for the two source recordings;
* actual `STOP → OPEN` and `STOP → CLOSE` actuator replay;
* event-level and recording-level CSV output; and
* integrated video and screenshot evidence.

Live EEG acquisition, online feature extraction, and closed-loop
feedback were outside the scope of this session.

## 3. Inputs and Fixed Dependencies

### 3.1 Frozen EEG-Derived Command Input

The canonical inputs were the frozen Session 16 decision-rule record
and command stream:

* subject: 1
* recordings: Run 1 and Run 2
* source rows: 118
* rows per recording: 59
* configuration: `win-2s_step-1s`
* selected rule:
  `thr-gap-mid__smooth-none__dwell-2`
* threshold: `threshold_gap_midpoint`
* smoothing: `smooth-none`
* dwell: 2 consecutive updates

The source recordings were:

* Run 1: `baseline_eyes_open`
* Run 2: `baseline_eyes_closed`

Session 19 did not recompute the EEG feature values or decision states.
It loaded the frozen command stream and validated the rule identity,
recording keys, row order, decision-time spacing, and command-state
vocabulary before constructing the replay plan.

### 3.2 Reused Actuator and Serial Components

The Session 17 actuator configuration and Session 18 serial contract
were reused without changing their endpoint, motion, or response
semantics.

The actuator configuration was:

* `CLOSE`: 60°
* startup position: 90°
* `OPEN`: 120°
* commanded-angle update: 2° every 50 ms

The serial configuration was:

* port: COM4
* baud rate: 9600
* protocol version: `S18_V0.1`
* expected startup message:
  `READY,S18_V0.1,STOP,90`
* one unresolved command at a time
* transmission of the next command only after a terminal `ACK` or `ERR`

The reusable `SerialClient` and serial-protocol parser from Session 18
handled port access, startup `READY`, command transmission, response
parsing, command-sequence assignment, and timestamped TX/RX events.

## 4. Replay Design and Implementation

### 4.1 Replay-Event Selection

For each source recording, Session 19 retained the first command row to
preserve the recording's initial command state. Subsequent events were
selected only when `command_state` changed from the preceding row.

Repeated rows with an unchanged command state were not transmitted.

| Recording | Source rows | Selected events | Omitted stable rows |
| ---------- | ----------: | --------------: | ------------------: |
| Run 1      |          59 |               2 |                  57 |
| Run 2      |          59 |               2 |                  57 |

### 4.2 Source-to-Replay Timing

For each recording, replay time was defined relative to its first
selected event:

```text
replay_time = source_time - first_selected_source_time
```

The 1.0 s interval between the two selected source events was therefore
retained in both replay runs.

| Run | Source time | Replay time | Source command | Serial command |
| --- | ----------: | ----------: | -------------- | -------------- |
| 1   |       2.0 s |       0.0 s | `CMD_STOP`     | `STOP`         |
| 1   |       3.0 s |       1.0 s | `CMD_OPEN`     | `OPEN`         |
| 2   |       2.0 s |       0.0 s | `CMD_STOP`     | `STOP`         |
| 2   |       3.0 s |       1.0 s | `CMD_CLOSE`    | `CLOSE`        |

Each command used an absolute monotonic replay target.

Schedule offset was calculated as:

```text
schedule_offset = actual_tx_time - scheduled_replay_time
```

If command or ACK processing extended beyond a replay target, the next
command was transmitted immediately and the positive offset was
retained in the event log. Subsequent targets were not shifted
cumulatively.

Schedule offset was logged as an execution-trace value and was not
included in the event PASS criterion.

### 4.3 Recording Execution Boundary

Run 1 and Run 2 were executed as independent replay runs.

Each recording used:

* a fresh `SerialClient`;
* a separate serial-port open and close cycle;
* an independent startup `READY` validation;
* a command sequence beginning at 1; and
* a replay clock beginning after startup handling.

A fixed 1.0 s startup-settle wait was applied after `READY` and before
the replay clock. A 1.0 s post-replay observation wait was applied after
the final command and remained outside the replay clock.

### 4.4 Expected ACK Validation

Expected response semantics were defined before command execution.

| Starting mode | Command | Expected result | Expected mode |
| ------------- | ------- | --------------- | ------------- |
| `STOP`        | `STOP`  | `DUPLICATE`     | `STOP`        |
| `STOP`        | `OPEN`  | `APPLIED`       | `OPEN`        |
| `STOP`        | `CLOSE` | `APPLIED`       | `CLOSE`       |

Each source event was linked to its serial response using:

* `source_event_id`, retained as the serial event `case_id`; and
* the host-side `command_seq`.

The source-linked event record included:

* source recording and window identity;
* source decision time;
* scheduled replay time;
* actual host TX time;
* schedule offset;
* ACK reception time;
* command–ACK round-trip time;
* expected and observed ACK result;
* expected and observed actuator mode; and
* event-level PASS/FAIL status.

### 4.5 Execution Modes and Safety Default

The script separated validation, READY testing, single-recording
replay, and integrated replay modes.

After the final integrated outputs were generated, the committed default
mode was returned to `validation_only`.

## 5. Results

### 5.1 Replay-Plan Validation

The frozen input and replay-plan validation produced:

* 118 validated source rows;
* two source recordings;
* four selected replay events;
* two recording-level replay plans; and
* no unexpected or missing recording keys.

The selected events were:

| Replay run     | Source event    | Source command | Serial command | Selection reason      |
| -------------- | --------------- | -------------- | -------------- | --------------------- |
| `S19-S001-R01` | `S001-R01-W000` | `CMD_STOP`     | `STOP`         | initial command state |
| `S19-S001-R01` | `S001-R01-W001` | `CMD_OPEN`     | `OPEN`         | command-state change  |
| `S19-S001-R02` | `S001-R02-W000` | `CMD_STOP`     | `STOP`         | initial command state |
| `S19-S001-R02` | `S001-R02-W001` | `CMD_CLOSE`    | `CLOSE`        | command-state change  |

### 5.2 READY Smoke Test

Two independent port-open cycles returned the expected startup message:

```text
READY,S18_V0.1,STOP,90
```

Each smoke-test run contained one RX `READY` event and zero transmitted
commands.

Both startup validations passed.

### 5.3 Actual Replay Result

The final integrated replay executed both recording plans using a fresh
serial connection for each recording.

| Replay run     | Command sequence | Observed ACK sequence            | Result |
| -------------- | ---------------- | -------------------------------- | ------ |
| `S19-S001-R01` | `STOP → OPEN`    | `DUPLICATE/STOP → APPLIED/OPEN`  | PASS   |
| `S19-S001-R02` | `STOP → CLOSE`   | `DUPLICATE/STOP → APPLIED/CLOSE` | PASS   |

All four transmitted events matched their expected ACK result and
actuator mode.

Operator observations were:

* visible opening-direction gripper movement during Run 1; and
* visible closing-direction gripper movement during Run 2.

### 5.4 Timing Trace

The final integrated replay produced the following timing trace:

| Run   | Command | Schedule offset | ACK round-trip time |
| ----- | ------- | --------------: | ------------------: |
| Run 1 | `STOP`  |      +16.000 ms |               31 ms |
| Run 1 | `OPEN`  |       +0.000 ms |               31 ms |
| Run 2 | `STOP`  |       +0.000 ms |               47 ms |
| Run 2 | `CLOSE` |       +0.000 ms |               31 ms |

All four ACKs were received before the next 1.0 s replay target.
ACK-based sequential transmission therefore did not delay a subsequent
command in the final integrated run.

### 5.5 Saved Outputs

The integrated replay saved and reloaded:

* four source-linked event rows;
* two recording-summary rows;
* four of four event-level PASS results;
* two of two recording-level PASS results; and
* matching source-event identities after CSV reload.

Saved-output validation passed.

## 6. Interpretation and Decisions

### 6.1 Interpretation

The first-row-plus-command-change policy reduced 118 frozen source rows
to four transmitted replay events while preserving each recording's
initial command state and subsequent command transition.

Independent serial connections, startup `READY` validation, and
recording-specific command sequences produced the expected
`STOP → OPEN` and `STOP → CLOSE` results without carrying host-side
serial state across recordings.

The observed ACK round-trip times of 31–47 ms remained below the 1.0 s
event interval, so ACK-based sequential transmission did not constrain
the replay schedule in the final integrated run.

Together with the source-linked event records and observed gripper
movement, these results establish a minimum offline source-to-actuator
replay demonstration using the frozen EEG-derived command stream.

### 6.2 Decisions

* Carry forward the first-row-plus-command-change event-selection policy
  and recording-specific replay clocks to subsequent replay work.
* Retain a fresh serial connection and startup `READY` validation for
  each source recording.
* Use the integrated event log and recording summary as the canonical
  Session 19 results for the Session 20 milestone record.
* Retain `validation_only` as the script's committed default mode.
