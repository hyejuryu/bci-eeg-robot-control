# Session 15 — Offline Decision Rule and Virtual Command-State Generation

**Planned period:** 2026-07-19 to 2026-07-23
**Actual work dates:** 2026-07-24 to 2026-07-27
**Status:** Completed

Session 15 applied candidate thresholds, causal smoothing, and consecutive-update dwell rules to the posterior-alpha feature stream selected in Session 14. The analysis generated threshold-state streams, confirmed command-state streams, command episodes, and rule-level summaries. Eight core rule configurations were examined, and the midpoint threshold with no smoothing and dwell-2 was retained as a provisional candidate for Session 16 review.

## 1. Objectives

1. Apply candidate thresholds to the posterior-alpha feature stream selected in Session 14.
2. Compare raw and causal median-3 feature streams using fixed threshold values.
3. Examine how dwell-1, dwell-2, and dwell-3 affect confirmed command switching and initialization timing.
4. Generate traceable offline threshold-state and command-state outputs.
5. Identify a provisional decision-rule candidate for the Session 16 milestone review.

## 2. Research Question

### Main question

How do threshold placement, causal smoothing, and dwell confirmation transform the selected posterior-alpha feature stream into an offline command-state stream?

### Subquestions

1. How does threshold placement affect `LOW_ALPHA` and `HIGH_ALPHA` states and confirmed command switching?
2. How do causal median-3 smoothing and dwell confirmation suppress brief command changes, and at which stage of the decision pipeline do they act?

## 3. What I Tested and How

### 3.1 Input feature stream

The analysis reused the window-level feature CSV generated in Session 14.

* Dataset: PhysioNet EEGBCI
* Subject: 1
* Run 1: baseline eyes open
* Run 2: baseline eyes closed
* Selected configuration: `win-2s_step-1s`
* Window length: 2.0 s
* Step size: 1.0 s
* Outer-window overlap: 50%
* Feature: `posterior_alpha_mean_psd`
* Unit: `V²/Hz`
* Source rows: 646
* Selected rows: 118
* Windows per run: 59
* Decision time: window end time
* Decision-time range: 2.0–60.0 s

The feature values were not recalculated in Session 15. The saved Session 14 values were used directly as the input to the decision-rule analysis.

### 3.2 Threshold calibration and rule-application order

Threshold candidates were first calculated from the unsmoothed baseline feature distributions.

```text
unsmoothed EO and EC feature distributions
→ fixed threshold candidates
```

Each rule was then applied in the following order:

```text
raw feature
→ optional causal smoothing
→ comparison with a fixed threshold
→ LOW_ALPHA or HIGH_ALPHA threshold state
→ dwell confirmation
→ active command state
```

The threshold state was stored in the output CSV as `evidence_state`. Its possible values were:

```text
feature < threshold       → LOW_ALPHA
feature >= threshold      → HIGH_ALPHA
feature unavailable       → UNAVAILABLE
```

The command mapping was:

```text
LOW_ALPHA   → CMD_OPEN
HIGH_ALPHA  → CMD_CLOSE
UNAVAILABLE → CMD_STOP
```

### 3.3 Threshold candidates

All three thresholds were calculated from the unsmoothed Session 14 baseline feature values.

| Threshold    | Definition                                   |      Value (`V²/Hz`) |
| ------------ | -------------------------------------------- | -------------------: |
| EO Q95       | 95th percentile of Run 1 raw features        | `8.270509057517e-11` |
| Gap midpoint | Geometric midpoint between EO Q95 and EC Q05 | `1.398718266196e-10` |
| EC Q05       | 5th percentile of Run 2 raw features         | `2.365528862351e-10` |

The quantiles used NumPy’s `linear` method.

The same threshold values were used for the raw and median-3 streams. This kept threshold placement fixed while the effect of smoothing was examined.

### 3.4 Causal smoothing

Two smoothing conditions were tested.

* `smooth-none`: the raw feature value was used directly.
* `smooth-median3`: the median of the current and previous two feature updates was used.

The median-3 calculation was causal and was reset at each recording boundary. The first two updates of each run did not contain enough values for a three-point median and were marked unavailable.

### 3.5 Dwell confirmation

Dwell values of 1, 2, and 3 consecutive available threshold states were tested.

The same dwell requirement was applied to:

* initialization from `CMD_STOP` to the first active command; and
* switching between `CMD_OPEN` and `CMD_CLOSE`.

The initial transition from `CMD_STOP` to an active command was treated as initialization rather than an active switch. Only confirmed `CMD_OPEN ↔ CMD_CLOSE` transitions were counted as active command switches.

When a threshold state differed from the active state, it was tracked as a candidate state. The active command changed only when the candidate count reached the required dwell value. An unconfirmed candidate at the end of a run was not force-confirmed.

### 3.6 Core rule configurations

The final core comparison contained eight rules.

| Rule ID                                | Threshold | Smoothing | Dwell |
| -------------------------------------- | --------- | --------- | ----: |
| `thr-eo-q95__smooth-none__dwell-1`     | EO Q95    | none      |     1 |
| `thr-gap-mid__smooth-none__dwell-1`    | midpoint  | none      |     1 |
| `thr-ec-q05__smooth-none__dwell-1`     | EC Q05    | none      |     1 |
| `thr-gap-mid__smooth-none__dwell-2`    | midpoint  | none      |     2 |
| `thr-gap-mid__smooth-none__dwell-3`    | midpoint  | none      |     3 |
| `thr-gap-mid__smooth-median3__dwell-1` | midpoint  | median-3  |     1 |
| `thr-gap-mid__smooth-median3__dwell-2` | midpoint  | median-3  |     2 |
| `thr-gap-mid__smooth-median3__dwell-3` | midpoint  | median-3  |     3 |

The comparison was expanded from the initially planned six rules to eight rules. The no-smoothing dwell-2 and dwell-3 conditions were added to separate dwell effects from smoothing effects.

The thresholds and rule behavior were derived and inspected using the same two baseline recordings. The results therefore describe within-recording calibration behavior rather than independent classification performance.

### 3.7 Rule and output consistency checks

The implementation was checked for:

* 118 selected feature rows, with 59 updates per run;
* decision times from 2.0 to 60.0 s at 1.0 s intervals;
* the expected threshold order of EO Q95 < midpoint < EC Q05;
* causal median-3 availability beginning at 4.0 s;
* smoothing and dwell-state reset at each run boundary;
* row-level equivalence before replacing the specialized rule paths with the generic rule builder;
* complete 0–60 s command-episode coverage; and
* expected output sizes after saving and reloading the CSV and JSON files.

The final outputs contained:

* 944 decision-stream rows;
* 42 command episodes;
* 16 rule-run summary rows; and
* one decision-rule metadata JSON file.

## 4. Key Results

A brief active episode was descriptively defined as an active `CMD_OPEN` or `CMD_CLOSE` episode lasting no more than 2.0 s. The initial `CMD_STOP` episode was excluded.

### 4.1 Rule-run summary

| Rule                          | First active command | Run 1 switches / brief episodes | Run 2 switches / brief episodes |
| ----------------------------- | -------------------: | ------------------------------: | ------------------------------: |
| EO Q95 / none / dwell-1       |                  2 s |                           4 / 2 |                           0 / 0 |
| Midpoint / none / dwell-1     |                  2 s |                           2 / 1 |                           0 / 0 |
| EC Q05 / none / dwell-1       |                  2 s |                           0 / 0 |                           4 / 2 |
| Midpoint / none / dwell-2     |                  3 s |                           0 / 0 |                           0 / 0 |
| Midpoint / none / dwell-3     |                  4 s |                           0 / 0 |                           0 / 0 |
| Midpoint / median-3 / dwell-1 |                  4 s |                           0 / 0 |                           0 / 0 |
| Midpoint / median-3 / dwell-2 |                  5 s |                           0 / 0 |                           0 / 0 |
| Midpoint / median-3 / dwell-3 |                  6 s |                           0 / 0 |                           0 / 0 |

### 4.2 Threshold placement

Under the EO Q95 threshold with no smoothing and dwell-1:

* Run 1 produced four active switches.
* Run 2 remained in `CMD_CLOSE` after initialization.

Under the midpoint threshold with no smoothing and dwell-1:

* Run 1 switched from `CMD_OPEN` to `CMD_CLOSE` at 26 s and returned to `CMD_OPEN` at 27 s.
* Run 2 remained in `CMD_CLOSE` after initialization.

Under the EC Q05 threshold with no smoothing and dwell-1:

* Run 1 remained in `CMD_OPEN`.
* Run 2 produced four active switches.

### 4.3 Raw and median-3 states at 26 s

At the Run 1 update ending at 26 s:

```text
raw feature value       = 2.232459066668e-10 V²/Hz
midpoint threshold      = 1.398718266196e-10 V²/Hz
causal median-3 value   = 3.958809706352e-11 V²/Hz
```

The raw value produced a `HIGH_ALPHA` state, while the median-3 value produced a `LOW_ALPHA` state.

Accordingly:

```text
raw + midpoint + dwell-1
→ CMD_CLOSE from 26 to 27 s

median-3 + midpoint + dwell-1
→ CMD_OPEN remained active
```

The raw `HIGH_ALPHA` state at 26 s corresponded to the local 24–26 s feature excursion decomposed in Session 14.

No raw-versus-median threshold-state differences were observed in Run 2.

### 4.4 Dwell confirmation

For the midpoint threshold without smoothing:

* Dwell-1 confirmed the single-update `HIGH_ALPHA` state at 26 s and produced a 1 s `CMD_CLOSE` episode.
* Under dwell-2, the candidate count reached 1 but did not reach the required count of 2. The active command therefore remained `CMD_OPEN`.
* Dwell-3 also produced no active switch.
* The first active command was confirmed at 3 s under dwell-2 and at 4 s under dwell-3.

For midpoint rules using median-3 smoothing:

* Dwell-1, dwell-2, and dwell-3 all produced zero active switches.
* Their first active-command times were 4, 5, and 6 s, respectively.

## 5. My Understanding

### 5.1 Threshold placement determined where within-run fluctuations became command changes

The lower EO Q95 threshold was more sensitive to elevated Run 1 values and produced several switches. The higher EC Q05 threshold kept Run 1 in `CMD_OPEN` but produced switches within Run 2.

The midpoint retained the main command state of each recording but converted the isolated Run 1 `HIGH_ALPHA` update into a brief command change when dwell-1 was used.

### 5.2 Smoothing and dwell acted at different stages

Median-3 smoothing changed the processed feature before threshold comparison. At 26 s, it changed the resulting threshold state from `HIGH_ALPHA` to `LOW_ALPHA`.

Dwell did not change the threshold state. Instead, it determined whether that state persisted for enough consecutive updates to change the active command.

Therefore:

```text
smoothing
→ may change LOW_ALPHA / HIGH_ALPHA itself

dwell
→ preserves the observed threshold state
→ controls whether it becomes an active command change
```

### 5.3 Additional stabilization introduced additional delay

In the current streams, dwell-2 and dwell-3 produced the same active
switch count. Dwell-3 did not reduce additional switches and delayed
the first active command by one second.

After median-3 smoothing changed the brief Run 1 `HIGH_ALPHA` state to
`LOW_ALPHA`, adding dwell-2 or dwell-3 did not reduce the active switch
count further. It only increased the initialization delay.

## 6. Decision

The provisional candidate for Session 16 review was:

* Threshold: midpoint
* Smoothing: none
* Dwell: 2 consecutive updates
* Rule ID: `thr-gap-mid__smooth-none__dwell-2`

Selection rationale:

1. **Threshold:** The midpoint produced one isolated `HIGH_ALPHA` update in Run 1, while the EO Q95 and EC Q05 conditions each produced four active switches in one of the recordings.
2. **Smoothing:** No smoothing retained the isolated raw `HIGH_ALPHA` state in the saved stream instead of changing it to `LOW_ALPHA` through median-3 smoothing.
3. **Dwell:** Under dwell-2, the candidate count reached 1 but not the required count of 2, so the active command remained `CMD_OPEN`.
4. **Comparison:** Dwell-2 produced zero active switches in both recordings and confirmed the first active command at 3 s. Dwell-3 produced the same switch result but confirmed it at 4 s.

**Status:** Provisional candidate. Decision rule v0.1 will be reviewed and locked in Session 16.

## 7. Questions / Unclear Points

1. Does dwell-2 retain the same switch suppression as dwell-3 on additional recordings while maintaining a shorter initialization delay?
2. Should threshold candidates be recalibrated from each processed feature stream, such as the causal median-3 stream, rather than transferred from the unsmoothed feature distribution?
3. How should brief threshold-state excursions be evaluated before deciding whether smoothing should remove them or preserve them?
